# Redis 父文档缓存设计要点

## 一、父文档缓存的定位

在父子分块架构里，Milvus 只保存子块向量和 `parent_id`，真正要送给大模型的是
几百到几千字的父块全文。这个全文存在 MySQL 里。

如果每次问答都回表 MySQL，看起来也没什么问题，因为主键查询很快。但在高并发场景下，
一次问答可能命中 5 到 10 个父块，如果逐个查询就是 N 次数据库往返，也就是典型的
N+1 查询问题，连接池会迅速被打满。

Redis 的价值就在这里：它把「N 次 MySQL 主键查询」变成「1 次 Redis MGET」，
把 2 到 5 毫秒的单次延迟压到 0.2 到 0.5 毫秒，并且几乎不消耗数据库连接。

## 二、Key 设计规范

推荐使用 `业务前缀:实体:主键` 的冒号分层结构，例如 `psd:parent:1024`。

这样设计有三个好处。一是便于批量扫描，用 `SCAN MATCH psd:parent:*` 可以定位全部
父文档缓存；二是便于权限与容量管理，可以按前缀做统计和清理；三是可读性好，
用 redis-cli 排查问题时一目了然。

绝对不要在 key 里放中文或超长内容，也不要使用 `KEYS *` 做扫描，
生产环境必须使用 `SCAN` 配合游标迭代，避免阻塞主线程。

## 三、缓存更新策略

父文档内容属于「读多写少、允许短暂不一致」的数据，最适合 Cache-Aside 模式。

读取时先查 Redis，命中就直接返回；未命中则回表 MySQL，拿到结果后顺手写回 Redis。
写入时先更新 MySQL（事实来源），再删除或覆盖 Redis 中的键。**不要先删缓存再写库**，
否则在并发场景下容易出现旧值被重新写回的脏数据。

对于父块这种内容确定、不会频繁变更的数据，也可以选择「更新时直接覆盖」而不是删除，
这样下次读取必定命中。

## 四、过期与内存管理

父文档缓存可以设置较长的过期时间，甚至永不过期，因为它是派生数据，
一旦源数据丢失可以随时从 MySQL 重建。

如果数据量非常大，必须设置 TTL 并配合 LRU 淘汰策略。设置 `maxmemory` 与
`maxmemory-policy allkeys-lru`，保证 Redis 在内存打满时淘汰冷数据而不是直接报错。

需要注意的是，一旦设置了 TTL，就要接受缓存穿透带来的回表压力。可以在业务层
加一层兜底：把「查询结果为空」也做短时间缓存，防止恶意请求反复穿透到数据库。

## 五、命中率观测

缓存是否有效，唯一可靠的指标是命中率，公式为 `hits / (hits + misses)`。

建议把计数写在 Redis 里而不是进程内存中，这样多实例部署时统计可以自然聚合，
重启应用也不会丢失数据。

如果命中率长期低于 60%，通常说明要么 key 设计有问题导致重复写入，
要么 TTL 太短，要么本来就没什么重复读取，这时候引入缓存反而增加了复杂度。

## 六、批量读取的正确姿势

单个 GET 循环 N 次是最常见的性能陷阱。应该使用 MGET 一次性取回 N 个键，
把网络往返从 N 次压缩到 1 次。

写入同理，应该使用 pipeline 批量提交，减少往返次数。但要注意 pipeline 不是事务，
如果业务上要求原子性，需要用 MULTI/EXEC 或者 Lua 脚本。
