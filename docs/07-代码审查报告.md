## 二、已发现并修复的问题

### 2.1 高危（4 项）

#### H1. 上传接口无防护：内存耗尽 + 任意文件解析

- **位置**：`app/api/routes.py` 的 `upload_document`
- **问题**：`raw = await file.read()` 一次性把整个文件读入内存，且不校验扩展名。
  构造超大文件即可耗尽进程内存；任意二进制文件会被当作 UTF-8 文本解析入库，产生垃圾数据。
- **修复**：新增 `read_upload_limited()` **流式分块读取**（超限立即返回 `413`，不读完整个文件）
  + `UPLOAD_ALLOW_EXT` **扩展名白名单**（不匹配返回 `400`）。
- **验证**：`tests/test_api_security.py`（单元：100B 通过 / 3MB 拒绝）
  + `tests/test_api_http.py::test_upload_rejects_disallowed_extension`（`.exe` → 400）
  + `test_upload_accepts_markdown`（`.md` 正常入库并可被检索）。

#### H2. 错误响应泄漏内部实现细节

- **位置**：`app/api/routes.py`（多处 `HTTPException(detail=f"...{exc}")`）、`app/api/main.py`（全局异常处理器）
- **问题**：把 `str(exc)` 直接返回给调用方，会暴露数据库连接串、表名、文件路径、
  第三方 SDK 报文（含内网地址）等，属于典型的信息泄露。
- **修复**：对外统一为通用文案（"入库失败，请查看服务端日志"），
  完整堆栈通过 `logger.exception` 记录；`health()` 中 Milvus 描述失败也只回通用提示。
- **验证**：`test_internal_error_does_not_leak_details` 断言响应体不含
  `Traceback` / `pydantic` / `site-packages` / `File "`；
  `test_health_survives_milvus_describe_failure` 断言不回显异常原文。

#### H3. CORS 配置无效且过宽

- **位置**：`app/api/main.py`
- **问题**：原为 `allow_origins=["*"]` **且** `allow_credentials=True`。
  这是浏览器会直接拒绝的无效组合，同时等价于"对所有站点开放凭证请求"。
- **修复**：改为 `CORS_ALLOW_ORIGINS` 来源白名单（默认仅本机）
  + **显式关闭** `allow_credentials` + 收窄允许的方法与头部。
- **验证**：`test_cors_middleware_is_restricted` 直接断言中间件真实 kwargs；
  `test_cors_origin_list_parsing_and_defaults` 断言默认不含 `*`。

#### H4. 健康检查被模型加载阻塞（可用性）

- **位置**：`app/api/routes.py:health()`、`app/api/main.py:lifespan`
- **问题**：`/health` 与 `/stats` 内部访问检索服务，而检索服务**懒加载** ——
  首次调用会连带加载嵌入模型（本机 BGE-M3 CPU 约 6~10s）与 jieba 词典。
  实测表现为 **健康检查超时**，上游/网关会误判服务不可用；第一个业务请求也要额外等待冷启动。
- **修复**：
  1. `WARMUP_ON_STARTUP=true`（默认）在启动阶段预热 BM25 词表 / 嵌入 / 重排，
     单组件失败只记日志并走降级路径（不阻断启动）；
  2. 监控接口**绝不触发**懒加载，未就绪时返回配置预期值并标注 `retrieval_ready=false`；
     `/stats` 同样改造；
  3. `/health` 自身永不抛异常（Milvus 元数据失败也只记录并返回 `milvus_error` 标记）。
- **验证**：`test_health_reports_config_values_without_loading_models`（未就绪时不初始化检索服务）、
  `test_health_survives_milvus_describe_failure`、`test_warmup_skipped_when_disabled`、
  `test_warmup_swallows_component_failures`。
- **实测**：`/health` 响应时间从 **超时（>10s）降到 0.061s**。

### 2.2 中危（6 项）

#### M1. 管理接口无任何保护

- **位置**：`app/api/routes.py` 的 `/admin/reindex`
- **问题**：该接口可**清空整个向量集合**，却不需要任何凭据；调试台上一键即可误触。
- **修复**：新增 `require_admin` 依赖，受 `ADMIN_TOKEN` 控制
  （非空时必须携带 `X-Admin-Token`）；未配置时保持本机免校验并在启动日志中**明确告警**。
- **验证**：`test_require_admin_*` 三个用例覆盖未配置 / 错误令牌 / 正确令牌。

#### M2. `/api/v1/parents/{id}` 响应随缓存状态抖动

- **位置**：`app/services/retriever.py:get_parent_document()`
- **问题**：缓存命中时只返回正文，**不返回元数据** →
  `doc_id` / `title` / `heading_path` / `child_count` 变成空值。
  调用方无法稳定获取这些字段，前端展示会时好时坏。
- **修复**：新增 `_fetch_meta()`（只 SELECT 元数据列，**不加载 LONGTEXT 正文**），
  元数据**始终**以 MySQL 为准；两条路径响应结构完全一致。
- **验证**：`test_parent_metadata_consistent_across_cache_states`（HTTP 层，连续两次读取）
  + `test_e2e_pipeline.py` 中对 `meta.doc_id` / `title` / `child_count` 的断言。

#### M3. 幽灵缓存：Redis 有残留但 MySQL 已删除

- **位置**：`app/services/retriever.py`
- **问题**：仅按缓存命中优先返回，若 MySQL 行已删除（异常中断、人工清理），
  接口会把已删除文档的内容当作有效结果返回。
- **修复**：`_fetch_meta()` 为 `None` 时判定为不存在并返回 `404`，
  以事实来源（MySQL）为最终判据。
- **验证**：`test_e2e_pipeline.py` 中构造 ghost key 并断言返回 `None`。

#### M4. `/stats` 被调试台轮询放大

- **位置**：`app/api/routes.py:stats()`
- **问题**：`redis_parent_keys` 依赖 `SCAN` 全量遍历（O(N)），而调试台每 20 秒轮询一次，
  并发访问时成本被持续放大。
- **修复**：增加 **5 秒记忆化**，并提供 `?force=true` 强制刷新；
  重置缓存统计时主动清空记忆化，保证计数类改动立即生效。
- **验证**：`test_stats_memoization_and_force`。

#### M5. `group_ms` 指标口径错误

- **位置**：`app/services/retriever.py`
- **问题**：该阶段从「Milvus 检索结束」起算，把 Rerank 耗时也算进"聚合去重"，
  指标名与含义不符 —— 会直接误导性能优化方向。
- **修复**：改为从 **Rerank 结束时刻**起算。
- **验证**：文档 `docs/01-架构与原理.md` §7 补充字段口径表。

#### M6. 缓存超时过短导致静默退化

- **位置**：`app/config.py`（`REDIS_SOCKET_TIMEOUT` 原为 5s）
- **问题**：高负载（如同时加载本地嵌入模型）时 5s 容易误判超时，
  入库时缓存写入被 `except` 吞掉（设计上可容忍），但会静默退化为回表、白丢缓存收益。
- **修复**：默认放宽到 **10s**，并在配置注释中说明"不建议调小"。
- **验证**：`test_redis_socket_timeout_is_generous`。

## 六、验收期间发现的环境问题（非代码缺陷）

最终回归时遇到两个**环境问题**，已定位并让测试对其免疫，特此记录：

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 重启机器后容器全停，`test_e2e_pipeline` 报 `MySQL 不可用`、演示测试 `pymilvus` 异常 | Docker Desktop 未随系统自启（现已由统一 compose 的 `restart: unless-stopped` 兜底） | 启动 Docker Desktop；必要时 `docker compose up -d` |
| 测试用 `urllib` 访问 `127.0.0.1:8000` 返回 404，但 curl / 浏览器正常 | **Windows 系统代理**（WinINET 注册表，实测 `127.0.0.1:26561`）被 `urllib.request.urlopen` 命中，本机地址也被路由到代理 | `urllib` 改用 `build_opener(ProxyHandler({}))` 强制本机直连（已固化到 `tests/test_api_http.py` 与 `scripts/check_local_models.py`） |

> 这两个问题说明：**面向"本机直连"的自动化，必须显式声明"不走代理"**；
> 且集成测试的**服务就绪探测**要用轮询而非一次性探测（服务启动会预热本地模型约 10~20s）。
> 二者均已作为经验写进相应代码注释与 `docs/06-配置说明.md` 排查表。
