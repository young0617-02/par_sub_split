# 架构与原理详解

本文说明本项目的设计原理、关键取舍与实测数据。所有数字均为本机实测（Milvus 3.0.0 /
MySQL 8.4 / Redis 8，3 篇样例文档，20 个子块）。

---

## 1. 整体架构与数据流

### 1.1 三存储分工

| 存储 | 存什么 | 为什么是它 |
| --- | --- | --- |
| **MySQL** | 父块全文 + 自增 `id` + 元数据 | 需要**强一致的持久化**和一个**全局唯一整数主键**作为跨存储锚点；内容大、更新少，天然适合关系库 |
| **Redis** | `psd:parent:{id}` → 父块全文 | 父块是**读多写少**的派生数据，`MGET` 把 N 次往返压成 1 次，延迟从毫秒级降到亚毫秒级 |
| **Milvus** | 子块稠密 + 稀疏向量 + `parent_id` | 需要**向量近邻检索**与**标量过滤**统一；稀疏/稠密同集合才能做服务端融合排序 |

为什么不把父块全文也存进 Milvus？因为向量库的 `VARCHAR` 字段是「随行返回」的，
不适合大文本：既不参与检索，又会放大每次查询的返回体积与内存占用。
**让每层存储只做它最擅长的事**，是本架构的核心原则。

### 1.2 入库时序

```
客户端 ──▶ IngestService.ingest_text()
              │
              ├─① split_document()            父块(1200字) + 子块(280字) 两级结构
              │
              ├─② MySQL INSERT                父块落库 → 拿到自增 parent_id
              │     └─ 回填：child.parent_id = 12, 13, ...
              │
              ├─③ Redis SET psd:parent:12     父块内容镜像（pipeline 批量）
              │
              └─④ Milvus UPSERT               子块稠密+稀疏向量 + parent_id
                    └─ 主键 = chunk_id(内容哈希) → 天然幂等
```

**顺序不可颠倒**：MySQL 是唯一事实来源，必须先落库拿到 `parent_id`，
才能给 Redis 的 key 和 Milvus 的 `parent_id` 字段赋值。

**一致性策略（务实版）**：

| 步骤 | 失败影响 | 处理 |
| --- | --- | --- |
| ② MySQL 失败 | 整次入库失败 | 直接抛错，事务回滚 |
| ③ Redis 失败 | 检索仍正确，只是慢一点 | 捕获告警，下次读时自动回表并回填 |
| ④ Milvus 失败 | 该文档查不到 | 抛错；因 `chunk_id` 幂等，重跑安全 |

### 1.3 查询时序（核心链路）

```
客户端 ──▶ RagService.answer()
              │
              ├─① 查询向量化
              │     ├─ 稠密：embedder.encode_query(q)      → [1024] float
              │     └─ 稀疏：encoder.encode(q)             → {idx: weight}
              │
              ├─② Milvus hybrid_search()
              │     ├─ AnnSearchRequest(dense,  anns_field=dense_vector,  COSINE, HNSW)
              │     ├─ AnnSearchRequest(sparse, anns_field=sparse_vector, IP,     倒排)
              │     └─ RRFRanker(60) 融合 → top 20 个**子块**
              │
              ├─③ 按 parent_id 聚合去重
              │     └─ 20 个子块 → 往往只对应 3~5 个父块
              │
              ├─④ Redis MGET 批量取父块全文（1 次 RTT）
              │     └─ 未命中 → 回表 MySQL WHERE id IN (...) → 回填 Redis
              │
              └─⑤ 组装 Prompt ──▶ LLM ──▶ 答案 + [父文档ID: x] 引用
```

## 2. MySQL 表设计

```sql
CREATE TABLE parent_document_t (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,  -- ★ 跨存储锚点
  doc_id        VARCHAR(64)  NOT NULL,                    -- 业务文档标识
  title         VARCHAR(255) NOT NULL DEFAULT '',
  heading_path  VARCHAR(512) NOT NULL DEFAULT '',         -- '手册 > 安装 > 环境要求'
  content       LONGTEXT     NOT NULL,                    -- ★ 喂给大模型的全文
  source        VARCHAR(512) NOT NULL DEFAULT '',
  chunk_index   INT          NOT NULL DEFAULT 0,
  child_count   INT          NOT NULL DEFAULT 0,
  char_count    INT          NOT NULL DEFAULT 0,
  content_hash  CHAR(64)     NOT NULL,                    -- sha256(父块内容)
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_pdt_doc_id (doc_id),
  UNIQUE KEY uk_pdt_doc_hash (doc_id, content_hash)       -- ★ 幂等约束
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

三个设计要点：

1. **`id` 必须自增整数**。它要同时出现在 Redis 的 key 和 Milvus 的 `parent_id` 里；
   如果用 UUID，会额外占用 Milvus 的 VARCHAR 字段并增加比较成本，且无法利用
   MySQL 的自增顺序做范围查询。
2. **唯一索引建在 `(doc_id, content_hash)` 而不是单独的 `content_hash`**。
   前者保证「同一文档内不重复」，同时允许**不同文档存在相同内容**
   （例如多份产品手册都有同一段免责声明）。后者会导致这种正常场景插入失败，
   并且按 `doc_id` 删除时会误删其他文档共享的父块。
3. **`content_hash` 用 sha256**。比 md5 更抗碰撞，且 64 字符定长便于写索引。

### 幂等实现

```python
existing = {row.content_hash: row for row in session.execute(
    select(ParentDocument).where(
        ParentDocument.doc_id == doc_id,
        ParentDocument.content_hash.in_(hashes),
    )
).scalars()}

for parent in parents:
    row = existing.get(parent.content_hash)
    if row is not None:      # 复用原 id，不重复插入
        parent_id = row.id
    else:                    # 新内容，插入并 flush 拿自增 id
        obj = ParentDocument(...); session.add(obj); session.flush()
        parent_id = obj.id
    for child in parent.children:
        child.parent_id = parent_id   # ★ key 回填到子块
```

`session.flush()` 而不是 `commit()`：立刻拿到自增主键，同时把提交时机留给外层
`session_scope()`，保证「一次入库 = 一个事务」。

## 3. Milvus 集合设计

```python
schema.add_field("chunk_id",      DataType.VARCHAR, is_primary=True, max_length=64)
schema.add_field("parent_id",     DataType.INT64)              # ★ 回表锚点
schema.add_field("doc_id",        DataType.VARCHAR, max_length=64)
schema.add_field("title",         DataType.VARCHAR, max_length=512)
schema.add_field("heading_path",  DataType.VARCHAR, max_length=512)
schema.add_field("chunk_index",   DataType.INT64)
schema.add_field("content",       DataType.VARCHAR, max_length=65535)   # 子块原文
schema.add_field("dense_vector",  DataType.FLOAT_VECTOR, dim=1024)
schema.add_field("sparse_vector", DataType.SPARSE_FLOAT_VECTOR)
```

### 3.1 主键用内容哈希，而不是自增

`chunk_id = sha256(f"{parent_index}|{index}|{content}")[:32]`，配合 `upsert`：

- 同一份文档重复入库 → 主键相同 → **覆盖而非新增**，不会产生重复向量；
- 内容变化 → 主键变化 → 新块入库，旧块由 `delete_by_doc_id` 清理。

这是「入库接口可被反复调用」的前提。

### 3.2 索引与度量

| 字段 | 索引 | 度量 | 理由 |
| --- | --- | --- | --- |
| `dense_vector` | HNSW（`M=64, efConstruction=200`） | **COSINE** | 向量已 L2 归一化，COSINE 与内积等价，但不受模长影响、更直观 |
| `sparse_vector` | SPARSE_INVERTED_INDEX（`DAAT_MAXSCORE`） | **IP** | 稀疏向量权重本身就是 BM25 分数，需要**加权求和**，不能再做余弦归一化 |

HNSW 参数取舍：

- `M`（每个节点邻居数）：越大召回越好、内存越大，常用 16~64；
- `efConstruction`（建索引搜索广度）：越大索引质量越高、构建越慢，常用 100~200；
- `ef`（查询参数，本项目取 `max(64, top_k*4)`）：在召回率与延迟之间权衡。

### 3.3 一致性级别：不要用 flush 换可见性

Milvus 默认 `Bounded` 一致性，新写入的数据可能延迟可见。常见做法是写入后调用
`flush()` 强制刷盘 —— 但 `flush` 会强制切段并重建段索引，**代价极高**：

| 方案 | 单篇文档入库耗时 |
| --- | --- |
| `Bounded` + 每次 `flush()` | **11592 ms** |
| `Strong` 一致性，不 flush | **81 ms** |

约 **140 倍**差距。正确做法是创建集合时指定 `consistency_level="Strong"`，
用读路径的一致性保证替代写路径的强制刷盘。

配套的第二个坑：`get_collection_stats().row_count` 依赖已落盘 segment，
不 flush 时长期显示 `0`。本项目改用 `query(count(*))` 走查询链路统计：

```python
res = self._client.query(
    collection_name=self.collection_name,
    filter="chunk_index >= 0",      # 所有实体都满足，等价于无条件
    output_fields=["count(*)"],
)
return int(res[0]["count(*)"])
```

## 4. 混合检索与融合排序

### 4.1 为什么需要稀疏分支

| 查询类型 | 稠密（语义） | 稀疏（BM25） |
| --- | --- | --- |
| 「怎么把数据存进向量库」→ 原文「向集合插入实体」 | ✅ 强 | ❌ 词不命中 |
| 「ERR_MILVUS_1001」这类错误码 | ❌ 训练语料几乎不出现，表示无区分度 | ✅ 精确命中 |
| 「SPARSE_INVERTED_INDEX」单名词查询 | ❌ 缺上下文，表示质量差 | ✅ 直接命中 |
| 「A100-80G」「张伟」等专有名词/低频词 | ❌ 容易漏召回 | ✅ 敏感 |

实测三路差异（`POST /api/v1/compare`，查询「RRF 和加权融合有什么区别？」）：

```
稠密分支命中父块: [1, 2, 3, 4]
稀疏分支命中父块: [2, 1, 4]
混合 RRF 命中父块: [1, 4, 2, 3]
稀疏独有父块: []   稠密独有父块: [3]   两路重叠: 3
```

### 4.2 RRF 倒数排名融合

对文档 d，在每一路结果里取它的排名 `rank_i`，然后：

```
score(d) = Σ_i  1 / (k + rank_i(d))          k 通常取 60
```

**为什么 `k=60`**：它把「排名第 1 与第 2 的差距」缩小到约 1.6%，
使得融合结果不会因为单路的排名抖动而剧烈变化，是一种平滑与鲁棒的折中。

**为什么 RRF 是安全默认**：它**只依赖排名，不依赖分数尺度**。稠密余弦分数在
`0.3~0.9`，BM25 分数（未归一化时）可能到 `30+`，直接相加会被 BM25 完全主导。
RRF 绕开了这个归一化难题。

### 4.3 加权融合

```python
WeightedRanker(0.7, 0.3)   # 稠密 0.7 + 稀疏 0.3，内部会做分数归一化
```

更灵活，但需要针对业务数据反复调参，且对异常分数敏感。建议：**先用 RRF 拿到基线，
再用加权融合做 A/B 对比**。

### 4.4 一个真实踩过的坑：父块加成必须用乘法

一次查询返回 20 个子块，往往有 6~8 个属于同一个父块。如果按 `parent_id` 聚合后
简单取 `max(子块分数)`，会丢失「多子块同时命中」这一强信号。最初的实现是：

```python
score = max(child_scores) + 0.05 * (len(hits) - 1)      # ❌ 加法
```

问题在于：**RRF 融合分数只有 `0.016~0.033` 量级**，而固定加法偏置 `0.05` 直接
盖过了真实排序信号，导致「命中 6 个子块但都不相关」的父块排到第一。

修正为相对加权：

```python
score = max(child_scores) * (1 + 0.15 * (len(hits) - 1))   # ✅ 乘法
```

乘法在 RRF（`0.03` 量级）和稠密余弦（`0.3` 量级）两种尺度下都保持相同的相对影响，
不会喧宾夺主。修正后最高分从 `0.28` 回到 `0.056`（= `0.0328 × 1.75`），
排序恢复正确。

### 4.5 低分过滤

只按 `top_k` 截断，会把「陪跑」父块也塞进 Prompt。增加相对阈值过滤：

```python
cutoff = best_score * settings.score_ratio_threshold   # 默认 0.2
targets = [p for p in ordered if scores[p] >= cutoff] or ordered[:1]
```

## 5. 父子分块策略

### 5.1 两级切分与硬边界

```python
text ──▶ _split_sections()      按 Markdown 标题切章节（维护标题栈 → heading_path）
     ──▶ _pack_units(父)        章节内段落打包到 1200 字，相邻块重叠 120 字
     ──▶ 跨小节合并              相邻短块继续合并到接近 1200 字
     ──▶ _join_headings()       生成 '手册 > 安装 ~ 环境要求' 章节标签
     ──▶ _pack_units(子)        父块内部按句子打包到 280 字，重叠 60 字
```

**必须遵守的硬边界**：子块绝不跨越父块。原因是 `parent_id` 只能存一个值，
若一个子块横跨两个父块，命中后回表哪个父块就说不清。因此切分顺序必须是
**先父后子**，而不是「先切小块再合并成大块」。

### 5.2 为什么必须补一步「跨小节合并」

只按 Markdown 标题切父块时，真实文档的小节往往只有 200~300 字，
父块会**退化到子块粒度**，父子分块失去意义。修正前后对比：

| 阶段 | 父块均长 | 子块均长 | 父子粒度比 |
| --- | --- | --- | --- |
| 仅按标题切 | 206~266 字 | 185~215 字 | ≈ 1.2 : 1（无意义） |
| 加入跨小节合并 | **726~1314 字** | 235~257 字 | **≈ 4 : 1（符合预期）** |

合并时保留所有覆盖到的章节名，只保留一次公共前缀：
`# 产品手册 / ## 安装说明 / ## 环境要求` → `产品手册 > 安装说明 ~ 环境要求`。

### 5.3 必须防止超长块

`_pack_units` 遇到「单个单元超过目标大小」时的朴素处理是「直接独立成块」，
这在整段没有句末标点的场景下会产出巨型块。实测：一段 2900 字、仅以顿号分隔的文本，
产出了 **1 个 2900 字的父块 + 1 个 2900 字的子块**，父子分块完全失效。

（真实对应场景：代码块、表格、清单、日志、压缩过的英文文本。）

修正为两级兜底：

```python
def _explode(text, size):
    if len(text) <= size:
        return [text]
    parts = [p for p in _SOFT_SEP_RE.split(text) if p.strip()]   # 顿号/逗号/分号/冒号
    if len(parts) > 1:
        return [p if len(p) <= size else _hard_wrap(p, size) for p in parts]
    return _hard_wrap(text, size)                                 # 完全没有分隔符 → 字符硬切
```

### 5.4 重叠比例

重叠控制在 **10%~20%**：太少会切断句子，太多会引入冗余并显著增加向量数量与成本。
本项目 `parent_overlap=120/1200=10%`、`child_overlap=60/280≈21%`。

## 6. BM25 稀疏向量实现

### 6.1 公式

```
score(q, d) = Σ_{t ∈ q}  IDF(t) · ( tf(t,d) · (k1 + 1) ) / ( tf(t,d) + k1 · (1 - b + b · dl/avgdl) )

IDF(t) = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )
```

- `k1 = 1.5`：控制词频饱和。`tf` 增大时分数趋近上限 `IDF·(k1+1)`，避免堆词作弊。
- `b = 0.75`：控制长度归一化强度，长文档不会仅因为长而得分高。

### 6.2 工程上必须解决的三件事

**① 词 → 整数下标的稳定映射**

Milvus 稀疏向量是 `{dim_index: weight}`，`dim_index` 是 `[0, 2^32)` 内的整数。
必须维护持久化词表 `data/index/vocab.json`：

> **最常见的事故**：入库时「安装」映射到下标 1024，查询时映射到 2048，
> 结果稀疏分支**静默返回空**（不报错！）。所以词表必须落盘、必须可复用。

**② IDF 依赖的全局统计量**

`df`（文档频率）、`N`（文档总数）、`avgdl`（平均文档长度）都需要跨请求复用，
存入 `data/index/bm25_stats.json`，入库时增量更新。

**③ 空稀疏向量会被 Milvus 拒绝**

如果文本分词后没有任何有效词（纯符号、纯停用词），必须塞一个占位下标：

```python
if not weights:
    return {EMPTY_TOKEN_ID: 1.0}    # EMPTY_TOKEN_ID = 0
```

**④ 训练顺序**：必须先 `fit()` 再 `encode()`，否则新词全部不在词表里，会被整批丢弃。

### 6.3 L2 归一化与权重压缩

对权重做 L2 归一化后，内积（IP）打分与余弦相似度等价，便于与稠密分支融合；
同时避免长文档因词量大而获得更高绝对分数。此外，`fit` 时按「文档」计数 `df`
（对 token 集合计数而非出现次数）才符合 BM25 定义。

## 7. 检索编排的细节

| 步骤 | 实现 | 说明 |
| --- | --- | --- |
| 聚合去重 | `grouped[parent_id].append(hit)` | 20 个子块 → 3~5 个父块，避免同一段内容重复进 Prompt |
| 父块打分 | `max(子块分) × (1 + 0.15 × 额外命中数)` | 多子块命中是强相关信号，但必须用相对加成 |
| 低分过滤 | `score >= best × 0.2` | 防止陪跑内容稀释关键信息、浪费 token |
| 批量取回 | `cache.mget(pids)` | 1 次 RTT 取回 N 个父块（对比 N 次 `GET`） |
| 回表兜底 | `WHERE id IN (...)` → 回填 Redis | Cache-Aside，Redis 抖动不会导致缺上下文 |
| 可解释性 | `explain=true` 时额外跑单分支 | 输出每个子块在稠密/稀疏分支中的排名 |

实测耗时分布（`top_k=20`，`final_top_k=4`，`hash` 占位向量）：

```
embed_ms ≈ 0.3   milvus_ms ≈ 5.5   rerank_ms ≈ 0    group_ms ≈ 0.03   redis_ms ≈ 2.2
total_ms ≈ 8~20（不含 LLM）
```

接入本地 BGE-M3（CPU）后：`embed_ms` 升至 **86~138ms**，检索合计约 **100~167ms**，
仍远低于 P95 < 800ms 的目标；真正的大头是 LLM 生成（**3.4~6.9s**）。

| 阶段字段 | 精确含义 |
| --- | --- |
| `embed_ms` | 查询向量化（稠密 + 稀疏） |
| `milvus_ms` | Milvus 混合检索（含 RRF 融合） |
| `rerank_ms` | Cross-Encoder 重排（未启用时约 0） |
| `group_ms` | 按 `parent_id` 聚合去重 + 父块打分 + 低分过滤 |
| `redis_ms` | `MGET` 批量取父块正文 |
| `mysql_fallback_ms` | 缓存未命中时回表 MySQL |
| `llm_ms` | 仅 `/chat`：大模型生成 |

> ⚠️ 注意：`group_ms` 必须从 **Rerank 结束时刻**起算。修复前它从 Milvus 结束时刻起算，
> 把重排耗时也算进了"聚合去重"，指标名与含义不符（已修复，见 CHANGELOG 1.1.0）。

`redis_ms` 约 2ms 中包含了「MGET + 命中率统计 pipeline」两次 RTT；
若对统计不敏感，可把统计改为异步批量写入。

## 8. Redis 缓存设计

### 8.1 Key 设计

```
psd:parent:12        → 父块全文（string）
psd:cache:hits       → 命中计数（INCR）
psd:cache:misses     → 未命中计数
psd:cache:requests   → 总请求数
```

`业务前缀:实体:主键` 的分层结构便于：按前缀 `SCAN` 统计与清理、按前缀做容量治理、
`redis-cli` 排查时一眼可读。

**不要用 `KEYS *`**，生产环境会阻塞主线程；本项目使用 `SCAN` + 游标迭代：

```python
def count_keys(self) -> int:
    return sum(1 for _ in get_client().scan_iter(match=f"{self.prefix}*", count=500))
```

### 8.2 Cache-Aside 模式

- **读**：先 Redis → 未命中回表 MySQL → 顺手回填 Redis；
- **写**：先更新 MySQL（事实来源），再删除或覆盖 Redis。

> **不要先删缓存再写库**。并发场景下，删缓存后、写库前的读请求会把旧值重新写回，
> 产生长期脏数据。父块内容确定、几乎不变，因此本项目写入时**直接覆盖**而非删除，
> 读取必然命中。

### 8.3 命中率统计放在 Redis 而不是进程内存

```python
pipe.incrby("psd:cache:hits", hits)
pipe.incrby("psd:cache:misses", total - hits)
pipe.incrby("psd:cache:requests", total)
```

好处：多实例部署时统计天然聚合；应用重启不丢数据；可直接接监控指标。
本机实测在演示流程中命中率稳定在 **100%**（父块写入后不会被淘汰）。

### 8.4 缓存命中率上不去怎么办

按以下顺序排查：

1. **key 是否被重复写入**：如果父块 id 每次都变（例如重复入库不断新增父块），
   缓存永远不命中。检查 `content_hash` 幂等是否生效。
2. **TTL 是否太短**：`REDIS_PARENT_TTL` 是否小于业务访问间隔。
3. **是否本来就没有重复读取**：一次性导入、从不查询的场景，缓存只会增加复杂度。
4. **容量淘汰**：是否设置了 `maxmemory-policy allkeys-lru` 且内存已满。

命中率长期低于 60% 时，先怀疑 key 设计与访问模式，而不是加大内存。

### 8.5 TTL 与内存治理

父块是派生数据，源数据在 MySQL，丢了可以随时重建，因此**可以永不过期**
（本项目默认 `REDIS_PARENT_TTL=0`）。数据量大时必须设置 TTL 并配置：

```
maxmemory 4gb
maxmemory-policy allkeys-lru
```

一旦引入 TTL，就要接受缓存穿透带来的回表压力，可在业务层对「查询结果为空」
做短时间缓存以防恶意穿透。

## 9. Prompt 设计与幻觉抑制

```
【回答要求】
1. 只使用片段中出现的信息，严禁编造或推测片段之外的内容；
2. 若片段信息不足以回答，请直接回答"根据已检索到的资料无法回答该问题"，并说明还缺少什么信息；
3. 引用某条片段时，在相应句子末尾标注其来源，格式为 [父文档ID: 12]；
4. 使用简体中文，先给结论，再给必要依据，条理清晰、不要啰嗦。
```

三点设计意图：

1. **限定信息源**：明确「仅依据片段」，是从 Prompt 层面抑制幻觉的第一道防线；
2. **允许说不知道**：显式给出「无法回答」的标准句式，避免模型勉强大段编造；
3. **强制引用**：`[父文档ID: x]` 让答案可回查原文，也便于定位检索质量问题。

**降级模式**：没有 API Key 时自动切换为抽取式回答 —— 按查询词重合度从父块中
抽取原句并标注出处，并明确标注 `【降级模式】`。这样离线也能验证链路，
同时**不说谎**：调用方从 `llm_mode` 字段就能知道这不是模型答案。

## 10. 可观测性

| 维度 | 观测点 | 暴露方式 |
| --- | --- | --- |
| 存储健康 | MySQL / Redis / Milvus 连通性 + 组件接线 + `retrieval_ready` | `GET /api/v1/health`（约 60ms，不触发模型加载） |
| 数据规模 | 父块数、子块数、文档数 | `GET /api/v1/stats` |
| 缓存效果 | 命中率、请求数、命中数 | `GET /api/v1/stats` |
| 阶段耗时 | `embed_ms / milvus_ms / group_ms / redis_ms / mysql_fallback_ms / llm_ms` | 每个检索与问答响应体的 `timings` |
| 检索质量 | 三路召回差异、分支内排名 | `POST /api/v1/compare`、`explain=true` |
| 分块质量 | 父/子块均长、最大块长 | 入库响应的 `detail.chunk_stats` |

**为什么阶段耗时必须拆开**：RAG 链路慢的时候，只有拆开才知道是向量化慢、
向量检索慢、Redis 慢还是 LLM 慢。本项目正是靠这个发现「入库 11.6 秒」的瓶颈在
`flush` 而不是向量计算。

## 11. 参数调优速查

| 症状 | 调整方向 |
| --- | --- |
| 召回不准，专有名词/错误码查不到 | 确认 `SPARSE_ENABLED=true`；检查停用词表，必要时扩充 |
| 召回不准，语义近似但用词不同查不到 | 换真实 Embedding 模型（`hash` 仅用于跑通链路） |
| 答案上下文不足 | 提高 `FINAL_TOP_K`（3→5）或 `PARENT_CHUNK_SIZE` |
| 答案被无关内容干扰 | 降低 `FINAL_TOP_K`、提高 `SCORE_RATIO_THRESHOLD` |
| 检索总命中同一父块 | 正常现象（说明该父块确实相关），已由聚合去重处理；若过多可减小子块重叠 |
| 向量库体积过大 | 减小 `CHILD_CHUNK_OVERLAP`、过滤低价值文档 |
| 入库太慢 | 检查是否误开 `flush`；批量接口 `upsert` 已合并为一次请求 |
| 指定章节没被单独召回 | 该章节过短，已被合并进相邻父块；可减小 `PARENT_CHUNK_SIZE` |

## 12. 安全与运维设计

本节记录 v1.1.0 全面审查后确定的安全边界，配套配置见 `docs/06-配置说明.md`。

### 12.1 信任边界

本系统默认定位为**内网服务**：业务接口（入库/检索/问答）不鉴权，
生产部署需在网关层补充认证与限流。已内置的防护针对"服务自身不成为攻击面"：

| 风险 | 防护 |
| --- | --- |
| 超大文件耗尽内存 | 上传**流式限量读取**，超限立刻 413（不把整个文件读进内存） |
| 任意文件被当文本解析 | 扩展名白名单（`UPLOAD_ALLOW_EXT`） |
| 错误响应泄漏内部信息 | 500 响应只给通用文案；堆栈仅进日志 |
| 管理接口被任意调用 | `ADMIN_TOKEN` + `X-Admin-Token` 请求头（未配置时打印告警） |
| CORS 配置失效/过宽 | 来源白名单 + 关闭凭证（`*` + credentials 是浏览器拒绝的无效组合） |
| SQL 注入 | 全部参数化；唯一动态 SQL（`CREATE DATABASE`）先做标识符白名单正则校验 |
| 向量 filter 注入 | `doc_id` 拼接前转义引号与反斜杠 |
| 凭据外泄 | 凭据只在 `.env`（gitignore）；`/health` 不回显任何凭据 |

### 12.2 缓存与事实来源的一致性

**MySQL 是唯一事实来源，Redis 只是派生缓存。** 由此推导出两条必须遵守的规则：

1. **元数据始终以 MySQL 为准**。`/api/v1/parents/{id}` 返回的
   `doc_id/title/heading_path/child_count` 不依赖缓存命中状态，
   避免响应字段随缓存抖动（只 SELECT 少数字段，不加载 LONGTEXT 正文，开销可忽略）。
2. **缓存残留不能覆盖事实**。Redis 中有 key 但 MySQL 行已删除时，接口返回 404
   而不是返回"幽灵"数据（`get_parent_document` 的 `_fetch_meta` 兜底判断）。

### 12.3 可观测性与成本控制

| 项 | 设计 |
| --- | --- |
| 阶段耗时 | 每次检索/问答都在响应体返回分阶段 `timings`，定位瓶颈无需翻日志 |
| 健康检查 | `/health` 返回三存储连通性 + 各组件实际接线（含 LLM 模式、向量 Provider、`retrieval_ready`） |
| **监控接口不触碰重型资源** | `/health` 与 `/stats` **绝不触发**嵌入/重排模型的懒加载，未就绪时返回配置预期值。否则首次健康检查会同步等待模型加载（本机 BGE-M3 CPU 约 6~10s）而**超时**，上游误判服务不可用。实测预热后 `/health` 约 **60ms** |
| 启动预热 | `WARMUP_ON_STARTUP=true`：启动阶段一次性加载 BM25 词表 / 嵌入 / 重排；单组件失败只记日志并走降级路径，不阻断启动 |
| 统计接口成本 | `redis_parent_keys` 依赖 `SCAN`（O(N)），调试台每 20s 轮询，故加 **5 秒记忆化**，并支持 `?force=true` |
| 单次检索成本 | `explain`（额外 2 次 Milvus 查询）改为**请求级开关**，默认关闭 |
| LLM 成本 | 单父块截断（`MAX_PARENT_CHARS`）+ 父块数上限（`FINAL_TOP_K`）+ 低分过滤三层控制 |

### 12.4 埋点口径必须与命名一致

`timings` 里的每个字段都必须能被信任，否则会误导优化方向。一个真实教训：
`group_ms` 最初从「Milvus 检索结束」起算，把 Rerank 的耗时也算进了"聚合去重"，
导致误以为分组逻辑慢。修复为从 **Rerank 结束**起算（见 CHANGELOG 1.1.0）。

同类原则也适用于"看似成功"的指标：`IngestResult.detail.redis_written` 为 0
**不代表**入库失败（Redis 是派生缓存，失败会自动回表），但必须如实上报，
且演示/测试不得把它当硬失败判据。
