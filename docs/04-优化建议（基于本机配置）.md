## 二、评估：分块策略

### 2.1 现状

| 参数 | 当前值 | 说明 |
| --- | --- | --- |
| `PARENT_CHUNK_SIZE` | 1200 | 父块目标字数（送模型） |
| `CHILD_CHUNK_SIZE` | 280 | 子块目标字数（做检索） |
| `PARENT_CHUNK_OVERLAP` | 120（10%） | 父块重叠 |
| `CHILD_CHUNK_OVERLAP` | 60（21%） | 子块重叠 |
| 结构处理 | 按 Markdown 标题切章节 → **跨小节合并**到目标大小 → 章节标签取首尾 | 已解决「父块退化成子块」问题（实测粒度比从 1.2:1 提升到 **4.3:1**） |
| 原子块保护 | 围栏代码块 / Markdown 表格**不按标点拆分**，超限时只按行边界拆 | 本次新增，避免故障码对照表被切断 |
| 超长兜底 | 次级分隔符 → 字符硬切 | 避免无标点文本产出 2900 字巨型块 |

### 2.2 针对本机语料（工业 IoT / 设备手册）的问题

本项目的语料特征是**短句 + 大量表格 + 大量错误码/型号 + 步骤列表**，与通用长文不同：

| # | 问题 | 依据 | 建议 |
| --- | --- | --- | --- |
| P1 | **子块 280 字偏大** | 故障手册单条处置步骤约 35~45 字，280 字会混入 5~6 条不相关内容，稀释向量 | `CHILD_CHUNK_SIZE=180~220`，`CHILD_CHUNK_OVERLAP=30~40`（降到 ~15%） |
| P2 | **父块 1200 字偏小** | 表格/步骤类内容信息密度高，1200 字常被切成两块，导致"答案在上半、现象在下半"被拆到两个父块 | `PARENT_CHUNK_SIZE=1600~1800`，`PARENT_CHUNK_OVERLAP=150` |
| P3 | **错误码可能被硬切** | `_hard_wrap` 按字符窗口切，理论上可切断 `E-1042`、`220±20N` | 在 `_explode` 前用正则把所有「实体片段」登记为不可切分点（见下方代码示意） |
| P4 | 子块丢失「块类型」信息 | 表格子块与段落子块混在一起，前端无法差异化展示 | 子块 schema 增加 `chunk_type`（`paragraph`/`table`/`code`）字段 |
| P5 | 无页面/来源定位 | PDF 场景无法回跳原页 | 子块 schema 增加 `page_no`、`source_offset` |
| P6 | 语义分块缺失 | 对**无 Markdown 标题**的纯文本（如 OCR 结果）只能按字数切 | 增加可选的「按句向量相似度断点」分块策略，作为 `CHUNKING_STRATEGY=semantic` 分支 |

**P3 代码示意**（保护不可切分实体）：

```python
# 在 chunker.py 的 _explode 之前先把实体替换为占位符，切分后再还原
_PROTECT_RE = re.compile(r"(E-\d{4}|ERR_[A-Z0-9_]+|[A-Z]{2,}-\d+[A-Z]?|\d+±\d+\s*(?:N|MPa|mm/s|℃))")
```

> 说明：这类「不切分保护」是工业知识库的常见刚需——**故障码被切断 = 检索永久失效**。

## 三、评估：检索效率

### 3.1 实测耗时基线（本机，3 篇样例文档，Milvus 20 个子块）

| 阶段 | `hash` 占位向量 | **本地 BGE-M3（CPU）** | 说明 |
| --- | --- | --- | --- |
| `embed_ms`（查询） | 0.32 ms | **86 ~ 138 ms** | BGE-M3 前向，CPU 推理 |
| `milvus_ms` | 5.54 ms | 6.6 ~ 13.0 ms | 稀疏+稠密混合检索 + RRF 融合（top-20） |
| `group_ms` | 0.04 ms | 0.05 ~ 0.07 ms | parent_id 聚合去重 |
| `redis_ms` | 2.67 ms | 2.9 ~ 6.6 ms | MGET + 命中率统计（2 次 RTT，首次含连接建立） |
| **检索合计** | **约 8.6 ms** | **约 100 ~ 167 ms** | 仍远低于 P95 < 800 ms 目标 |
| LLM 生成 | — | **3.4 ~ 6.9 s** | qwen2.5:7b（含首次加载）；暖机后约 4.3 s |
| 入库（每篇 6~7 子块） | 50 ~ 650 ms | **2.3 ~ 3.6 s** | 其中嵌入占绝大部分（CPU ≈ 400 ms/子块） |

**结论：检索链路本身很轻，成本集中在「嵌入 + LLM 生成」**。因此优化重点是
**召回质量**（换真模型、加重排）与**索引吞吐**（索引期把嵌入切到 GPU fp16），
而不是继续压榨那几毫秒。

### 3.2 ✅ 已修复：`/search` 默认开启 explain

原实现每次检索都会额外跑稠密、稀疏两个单分支查询：

```python
# 修复前（routes.py）
explain=True          # 无条件执行，检索耗时直接翻倍

# 修复后
explain=req.explain   # SearchRequest.explain，默认 False
```

优化空间：**P95 延迟降低约 40~50%**（3 次 Milvus 查询 → 1 次）。

### 3.3 建议：稀疏分支从「自研 BM25」切到「BGE-M3 稀疏头」

| 维度 | 自研 BM25（现状） | BGE-M3 稀疏（建议） |
| --- | --- | --- |
| 效果 | 词匹配，无法处理同义/词形 | **学习得到的词权重**，含同义泛化能力 |
| 维护成本 | 需持久化 `vocab.json` + `bm25_stats.json`，**词表不一致会导致稀疏分支静默返回空** | 无词表维护（模型自带 tokenizer） |
| 计算成本 | 纯 CPU，几乎为 0 | **与稠密共享一次前向**，边际成本极低 |
| 工程改动 | — | `embedder.encode_documents` 同时返回 dense + sparse |

**建议**：保留 BM25 作为**对照基线**（可通过 `SPARSE_BACKEND=bm25|bge_m3` 切换），
默认切到 `bge_m3`，这样既拿到效果提升，又保留了可对比的降级路径。

### 3.4 建议：开启 Rerank（本机已有模型）

本次已实现可选的 Cross-Encoder 重排层（`app/services/reranker.py`），默认关闭。

**关键设计决策：重排作用在「子块」而不是「父块」**，理由：

1. 子块才是检索单元，用父块重排等于换粒度重新排序，破坏「子块检索」的前提；
2. cross-encoder 计算量随文本长度增长，280 字 vs 1200 字差 4 倍以上；
3. 子块分数可在同一尺度比较，便于保留「多子块命中」信号。

配置方式：

```bash
RERANK_ENABLED=true
RERANK_MODEL=BAAI/bge-reranker-v2-m3
RERANK_DEVICE=cpu        # 见 §4.1 显存分析，默认 CPU
RERANK_CANDIDATES=20     # 重排窗口：对混合检索 top-20 子块重排
RERANK_KEEP=10           # 重排后保留 10 个，再按 parent_id 聚合
```

预期收益：**Recall@5 / 答案命中率明显提升**，代价是每次查询增加
「20 条 × 280 字」的 cross-encoder 前向（CPU 上约 200~600ms，仍在 P95 预算内）。

### 3.5 建议：Redis 两级缓存与统计异步化

| # | 优化 | 说明 |
| --- | --- | --- |
| 1 | 进程内 LRU（一级） + Redis（二级） | 热父块走内存（~0.01ms），Redis 兜底；父块内容几乎不变，一致性风险可控 |
| 2 | 命中率统计异步上报 | 当前每次查询多 1 次 RTT（`INCRBY` pipeline），占 `redis_ms` 约一半；改为后台批量写 |
| 3 | 缓存预热 | 服务启动时批量加载高频父块（可用历史查询日志统计） |

### 3.6 建议：Milvus 侧优化

| # | 优化 | 触发条件 |
| --- | --- | --- |
| 1 | 为 `doc_id` 建**标量索引** | 现在删除/过滤走全表扫描，语料大后变慢 |
| 2 | 按 `doc_id`/租户**分区（partition）** | 单集合实体 > 100 万，或存在多租户隔离需求 |
| 3 | 用 `expr` 做租户/权限过滤 | 已有能力，只需加字段 |
| 4 | `ef` 随 `top_k` 动态调整 | 已实现 `max(64, top_k*4)`；可加入离线召回率-延迟曲线做定参 |
| 5 | 定期 `compact` | 频繁 upsert 后段碎片增多 |

## 四、评估：参数设置

### 4.1 显存预算（最硬的约束）

实测：`8188 MiB` 总量，**`5785 MiB` 已被 LLM 占用**，剩余 `~2403 MiB`。

| 组件 | fp32 权重 | fp16 权重 | 是否可放入剩余显存 |
| --- | --- | --- | --- |
| BGE-M3（嵌入） | ~2.1 GB | ~1.1 GB | fp16 **勉强**（+激活值易超） |
| bge-reranker-v2-m3 | ~2.1 GB | ~1.1 GB | fp16 **勉强** |
| 嵌入 + 重排同时 | — | ~2.2 GB | ❌ 必爆 |

**结论与建议**：

```
推荐调度（本项目默认配置）
─────────────────────────────────────────────
LLM (qwen2.5:7b)   → GPU 常驻     （~5.8GB，keep_alive 保活）
BGE-M3 嵌入         → CPU          （EMBEDDING_DEVICE=cpu）
bge-reranker 重排   → CPU          （RERANK_DEVICE=cpu）
─────────────────────────────────────────────
可选加速方案
① 索引阶段（离线、可容忍慢）：临时停 LLM 占用，把嵌入切 cuda+fp16
   ollama stop qwen2.5:7b   →  EMBEDDING_DEVICE=cuda, EMBEDDING_FP16=true
② 查询阶段（延迟敏感）：保持重排在 CPU，避免与 LLM 争抢显存
③ 若必须三者上 GPU：需先给 Ollama 设置 num_ctx=4096 并把 keep_alive 调小
```

本项目已把 `EMBEDDING_DEVICE` / `EMBEDDING_FP16` / `RERANK_DEVICE` / `RERANK_FP16`
做成配置项，切换不需要改代码。

### 4.5 ⚠️ 实测发现：7B 小模型的「假拒绝」问题（已修复）

**现象**：父子分块链路完全正确（父块确实包含全部 5 条处置步骤，检索阶段断言 5/5 通过），
但 `qwen2.5:7b` 却回答：

> 「根据已检索到的资料无法回答该问题。因为【父文档片段】中并未提供报警代码 E-1042
> 的具体处理方法，仅提供了其他报警代码的处理建议。」

它甚至自己矛盾：同一句里既说"片段提供了处置步骤"又说"未提供"。
**更关键的是：同一问题、同一上下文，前一次运行给出了完整答案，这次却拒绝了**
——说明这是**不稳定的模型行为**，不是链路问题。

**根因分析**：

1. **拒绝模板的"锚定效应"**：原 Prompt 直接给出 `"根据已检索到的资料无法回答该问题"`
   这一整句模板。小模型的指令遵循能力弱，容易把模板当成"必须输出的一句"，
   在信息其实充足时也照抄一遍。**给拒绝话术反而提高了拒绝率**，这是反直觉但常见的坑。
2. **缺少"先检查再决定"的推理步骤**：原 Prompt 没有要求模型逐条核对片段，
   模型倾向于快速给出安全（保守）的答案。
3. **温度 0.2 对 7B 模型偏高**：小模型在临界判断上对温度更敏感。

**修复措施**（已落地在 `app/services/llm.py`）：

```text
1. 先逐条检查每个片段是否包含与问题相关的信息（故障码、型号、操作步骤、参数值…）。
   只要存在相关信息，就必须据此作答。
2. 不要轻易回答"无法回答"：只有当所有片段都与问题完全无关时才允许；
   片段中包含答案却回答无法回答，属于严重错误。   ← 关键：把"假拒绝"定义为错误
3. 信息不完整时，先给出片段能支持的部分，再说明还缺少什么。   ← 替代"整体拒绝"
```

同时把 `LLM_TEMPERATURE` 从 `0.2` 降到 `0.1`。

**验证结果（连跑 3 次）**：

| 次数 | 处置步骤覆盖 | 是否出现"无法回答" | LLM 耗时 |
| --- | --- | --- | --- |
| 第 1 次 | **5/5** | 否 | 6406 ms |
| 第 2 次 | **5/5** | 否 | 4349 ms |
| 第 3 次 | **5/5** | 否 | 4353 ms |

→ **3/3 稳定给出完整答案**，假拒绝消失。

**通用建议**：接入 7B 级本地模型做事实型 RAG 时，
① 不要在 Prompt 里直接给出完整的拒绝话术；
② 用"如果不包含答案才允许拒绝，否则视为错误"这种**反向约束**；
③ 对答案覆盖率做自动化断言（本项目 `tests/test_parent_child_demo.py` 已内置），
把"模型行为回归"纳入测试而不是靠人工抽查。

## 六、评估方法（可复用）

本项目演示文件（`tests/test_parent_child_demo.py`）已经内置了一个**可量化的效果指标**，
建议把它扩展成常规回归评估：

| 指标 | 定义 | 本项目示例值 |
| --- | --- | --- |
| **答案覆盖率** | 送进模型的上下文中，命中了多少条"标准答案要点" | 小块 RAG **0/5** vs 父子分块 **5/5** |
| Recall@k | 正确父块是否出现在前 k 个结果中 | 待标注集补充 |
| MRR | 正确父块的排名倒数均值 | 待标注集补充 |
| 缓存命中率 | `hits / requests` | 演示中重复查询达 **100%** |
| 阶段耗时 | `embed/milvus/group/redis/rerank/llm` 分级 | 检索合计约 8.6ms |

> 「答案覆盖率」比单纯的检索相似度分数更贴近业务：**用户关心的是答案有没有被送进去**，
> 而不是某个块的余弦相似度是多少。

## 七、一句话总结

> 本机配置**足以支撑**这套父子分块 RAG：LLM 走 Ollama(11434)、嵌入/重排用本地
> BGE-M3 与 bge-reranker-v2-m3（1024 维与现有集合完全对齐，**无需改表**）。
> 真正的瓶颈**不是检索耗时（BGE-M3 下约 100~167ms，仍远低于 800ms 目标），而是三件事**：
> ① **向量质量**（`hash` 必须换 BGE-M3 —— 本次已完成并实测）；
> ② **小模型行为**（7B 会出现"假拒绝"，必须用反向约束的 Prompt 压制 —— 本次已修复并验证 3/3 稳定）；
> ③ **显存预算**（8GB 已被 7B LLM 占用 5.8GB，
> **嵌入与重排默认走 CPU 是最稳妥的选择**，索引期可临时停 LLM 切 GPU fp16 加速）。
>
> 下一步优先级：开启子块级 Rerank → 把子块降到 180~220 字 → 建立 20~30 条标注问答做回归，
> 让后续每一次调参都有客观依据。
