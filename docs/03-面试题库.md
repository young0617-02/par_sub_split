# 面试题库（含参考答案）

共计 **45 题**，分四类：基础概念（12）、核心原理（14）、应用场景（9）、高频考点（10）。
参考答案均结合本项目的真实实现，不是通用套话。

## 一、基础概念（12 题）

### Q1. 什么是父子分块（Parent-Child Chunking）？

把文档切成**两级粒度**：较大的「父块」和较小的「子块」，子块记录其所属父块的标识。
**用子块做向量检索**（粒度小、语义聚焦、召回准），**用父块作为大模型上下文**
（内容完整、不断章取义）。它解决的是 RAG 中「检索粒度」与「生成粒度」的矛盾。

本项目：父块 1200 字入 MySQL 并镜像到 Redis，子块 280 字入 Milvus 并携带 `parent_id`。

### Q2. 为什么不能只切一种粒度？

- 只切小块（200 字）：检索准，但上下文残缺，大模型断章取义；
- 只切大块（2000 字）：上下文完整，但向量被无关信息稀释，检索差且 Prompt token 暴涨；
- 这是一个**结构性矛盾**，调参只能缓解，无法同时满足。

### Q3. 什么是稀疏向量和稠密向量？

- **稠密向量**：固定长度的浮点数组（如 1024 维），每维都有值，表达**语义**，
  通过 Embedding 模型生成，擅长语义泛化，不擅长精确词匹配。
- **稀疏向量**：`{下标: 权重}` 的映射，绝大多数维度为 0，表达**词的重要性**，
  通过 BM25/TF-IDF 或 SPLADE 生成，擅长专有名词、错误码、低频词精确命中。

### Q4. 什么是混合检索（Hybrid Search）？

同时执行稀疏检索与稠密检索，再把两路结果**融合排序**。
本项目用 Milvus 的 `hybrid_search(reqs=[稠密请求, 稀疏请求], ranker=RRFRanker(60))`
在同一集合内完成，避免了两套系统的结果合并成本。

### Q5. RRF 是什么？

Reciprocal Rank Fusion，倒数排名融合：`score(d) = Σ 1/(k + rank_i(d))`，`k` 通常取 60。
**只依赖排名、不依赖分数尺度**，因此不需要做分数归一化，是混合检索最安全、
最省调的默认融合策略。

### Q6. Redis 在架构里承担什么角色？

缓存「父块全文」。Milvus 只能给出 `parent_id`，最终要取几百到几千字的父块内容，
Redis 用 `MGET` 把 N 次 MySQL 主键查询压成 1 次往返，延迟从毫秒级降到亚毫秒级，
且几乎不消耗数据库连接。

### Q7. 为什么子块必须携带 `parent_id`？

因为检索命中子块后，必须知道「该把哪一段完整内容交给大模型」。
`parent_id` 是连接向量库与父文档存储的唯一锚点，也是 Redis cache key 的组成部分。

### Q8. MySQL 在这套架构里为什么不可替代？

它是**唯一事实来源（Source of Truth）**：父块全文的持久化、自增主键的生成、
幂等约束（唯一索引）和事务能力。Redis 与 Milvus 的数据都可以从 MySQL 重建。

### Q9. `upsert` 和 `insert` 在向量库里的区别？本项目为什么用 `upsert`？

`insert` 按主键追加（重复主键报错或产生重复数据）；`upsert` 按主键覆盖。
本项目主键是**内容哈希**，因此 `upsert` 让「同一文档重复入库」天然幂等，
不会产生重复向量 —— 这是入库接口可以被安全重复调用的前提。

### Q10. 什么是 Cache-Aside 模式？

读时先查缓存，未命中回查数据库并回填缓存；写时先更新数据库，再删除或覆盖缓存。
本项目读路径完全遵循该模式，并在 Redis 读失败时**回表 MySQL 兜底**，
保证缓存故障不会导致答案缺上下文。

### Q11. 向量检索里的 Top-K 指什么？和最终送模型的块数是一回事吗？

不是。`top_k` 是 Milvus 召回的**子块**数（本项目 20）；`final_top_k` 是按 `parent_id`
去重后送入大模型的**父块**数（本项目 4）。两者粒度不同、目的不同：
前者追求查全（召回率），后者追求查准与 token 成本。

### Q12. 为什么父块内容要存两份（MySQL 和 Redis）？

职责不同：MySQL 负责**持久与一致**（可以重建、可以做事务、可以按条件查询），
Redis 负责**低延迟读取**。父块是「读多写少、可容忍短暂不一致」的派生数据，
是典型的缓存友好场景。也存在一份（只存 MySQL）的方案，代价是每次问答多几次数据库往返。

## 二、核心原理（14 题）

### Q13. Milvus 里稀疏向量怎么表示？有哪些必须注意的工程细节？

表示为 `{dim_index: weight}`，`dim_index ∈ [0, 2^32)`。三个必须注意的点：

1. **词到下标必须是稳定映射，且要持久化**。入库时「安装」映射到 1024、
   查询时映射到 2048，稀疏分支会**静默返回空**（不报错），这是最隐蔽的坑。
2. **不接受空稀疏向量**。分词后无有效词时必须塞占位下标（本项目用 0）。
3. **必须先统计再编码**。新词不在词表里会被整批丢弃，所以要先 `fit()` 再 `encode()`。

### Q14. 为什么稠密索引用 COSINE、稀疏索引用 IP？

稠密向量已做 L2 归一化，此时内积与余弦等价，用 COSINE 更直观且不受模长影响。
稀疏向量的权重本身就是 BM25 分数，需要的是**加权求和**；若再做余弦归一化，
会破坏 BM25 的量纲与「词权重直接可比」的性质，因此必须用 IP。

### Q15. BM25 的公式和参数含义？

```
score(q,d) = Σ_{t∈q} IDF(t) · ( tf(t,d)·(k1+1) ) / ( tf(t,d) + k1·(1 - b + b·dl/avgdl) )
IDF(t) = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )
```

- `k1`（本项目 1.5）：词频饱和系数。`tf` 增大时分数趋近上限 `IDF·(k1+1)`，抑制堆词作弊；
- `b`（本项目 0.75）：长度归一化强度，`b=1` 完全归一化，`b=0` 不归一化；
- `IDF` 的 `+0.5` 平滑保证不会出现负值。

### Q16. RRF 的 `k` 为什么取 60？

`1/(k+rank)` 中，`k` 越大，相邻排名的分数差距越小，融合结果越平滑、越鲁棒。
`k=60` 让 rank 1 与 rank 2 的差距缩小到约 1.6%，避免单路排名抖动主导最终结果，
是经验上的稳健取值。

### Q17. 加权融合（WeightedRanker）和 RRF 怎么选？

| | RRF | WeightedRanker |
| --- | --- | --- |
| 依赖 | 只看排名 | 需要分数归一化 |
| 调参 | 基本不用 | 权重要按业务调 |
| 风险 | 丢失分数强弱信息 | 对异常分数敏感 |
| 建议 | **先拿基线** | 有标注数据后再 A/B 优化 |

### Q18. 按 `parent_id` 去重后，父块的分数怎么算？

本项目：`score = max(命中子块分数) × (1 + 0.15 × (命中子块数 - 1))`。

**为什么必须用乘法**：RRF 融合分数只有 `0.016~0.033` 量级，而稠密余弦分数在
`0.3~0.9` 量级。如果用固定加法偏置（如 `+0.05×(n-1)`），在 RRF 场景下会直接
盖过真实排序信号，让「命中 6 个子块但都不相关」的父块排到第一。
乘法在两种尺度下保持相同的相对影响。

### Q19. RAG 检索为什么容易「一个父块霸屏」？怎么处理？

因为一个父块包含多个子块，高度相关时多个子块会同时被召回（本项目实测 top-20 中
有 6~8 个属于同一父块）。处理方式是**按 `parent_id` 聚合去重**，
同时对多命中的父块给一个**相对**奖励。若不加去重，同一段内容会被重复拼进 Prompt，
既浪费 token 又干扰模型判断。

### Q20. 为什么子块不能跨越父块边界？

因为 `parent_id` 字段只能存一个值。若一个子块横跨两个父块，命中后无法唯一确定回表哪个父块。
因此切分顺序必须是**先切父块，再在父块内部切子块**，而不是「先切小子块再合并」。

### Q21. 父块一定要比子块大很多吗？粒度比多少合适？

一定要，否则父子分块没有意义。本项目实测：只按 Markdown 标题切父块时，
父块均长 206~266 字、子块 185~215 字，**粒度比约 1.2:1，等于退化**；
加入「跨小节合并」后父块 726~1314 字、子块 235~257 字，**粒度比约 4:1**。
经验上父块 1000~2000 字、子块 200~400 字比较合适。

### Q22. 分块重叠（overlap）设多少？太大会怎样？

建议 10%~20%。太小会切断句子导致语义不完整；太大会引入大量冗余，
**显著增加向量数量与存储成本**，而且会让同一父块在 top-k 中重复出现。
本项目父块重叠 10%（120/1200）、子块重叠约 21%（60/280）。

### Q23. Milvus 为什么不建议用 `flush` 保证写入可见性？

`flush` 会强制切段并重建段索引，代价极高。本项目实测：`Bounded` + 每次 `flush`
单篇入库 **11592 ms**，改用 `consistency_level="Strong"` 后降到 **81 ms**，
差约 140 倍。正确做法是用**读路径的一致性级别**替代**写路径的强制刷盘**。

### Q24. `get_collection_stats().row_count` 能当准确值吗？

不能。它依赖已落盘 segment，不 flush 时会长期显示 0（本项目就踩过：明明写入了 20 条，
却显示 `row_count = 0`）。应改用 `query(filter="...", output_fields=["count(*)"])`，
走查询链路得到实时准确值。

### Q25. Redis 缓存命中率低，你会怎么排查？

按顺序检查四件事：

1. **key 是否被重复写入** —— 如果每次入库都新增父块（幂等失效），父块 id 一直变，
   缓存永远不命中。先查 `content_hash` 唯一索引是否生效。
2. **TTL 是否太短** —— `REDIS_PARENT_TTL` 小于业务访问间隔。
3. **是否本来就没有重复读取** —— 一次性导入、只查一次的场景，缓存只会增加复杂度。
4. **是否被容量淘汰** —— 检查 `maxmemory-policy` 是否 `allkeys-lru` 且内存已满。

命中率长期低于 60% 时，优先怀疑 key 设计与访问模式，而不是加大内存。

### Q26. 为什么缓存命中率统计要放在 Redis 而不是进程内存？

多实例部署时，进程内计数无法聚合，每个实例只看到自己那部分的命中率；
应用重启后数据全部丢失；也无法直接被监控系统采集。
放进 Redis 用 `INCRBY` 累加，可以实现跨实例聚合、重启不丢、直接对接监控。

## 三、常见应用场景（9 题）

### Q27. 什么场景最适合父子分块？

1. **长技术文档 / 产品手册问答**：章节结构清晰，需要「小节级检索 + 段落级上下文」；
2. **法律/合同条文问答**：需要定位到具体条款（子块），但必须给出完整条款上下文（父块）；
3. **企业知识库**：制度、流程类文档，答案常常需要跨段落综合。

**不适合**：单句短文本（FAQ 一问一答）、高度结构化的表格数据（应走 NL2SQL）、
纯实时数据（应走 API 工具调用）。

### Q28. 稀疏分支在什么业务场景下价值最大？

专有名词、错误码、型号、人名、内部黑话密集的场景。例如：

- 运维知识库里的 `ERR_MILVUS_1001`、`OOMKilled`、`CrashLoopBackOff`；
- 电商的商品型号 `A100-80G`、SKU 编码；
- 金融的风控规则编号、监管文号。

这些词在 Embedding 模型训练语料中几乎不出现，稠密向量表示无区分度，稀疏分支能精确命中。

### Q29. 向量库选型：Milvus / pgvector / Elasticsearch 怎么选？

| 方案 | 适用 | 权衡 |
| --- | --- | --- |
| **Milvus** | 亿级向量、需要稀疏+稠密同库融合、强标量过滤 | 组件多（etcd+minio+节点），运维成本高 |
| **pgvector** | 千万级以内、已有 PG、想少一个组件 | 大规模性能与索引类型不如专用库 |
| **ES/OpenSearch** | 已有 ES、需要强文本检索与聚合 | 向量检索能力相对弱，(k)NN 是后加的 |

本项目的选型理由：**需要稀疏向量与服务端融合排序**，这是 Milvus 的原生能力。

### Q30. 三存储架构在高并发下有哪些风险点？

1. **N+1 查询**：一次问答命中多个父块，若逐个查 Redis/MySQL 会放大往返 —— 必须 `MGET`；
2. **连接池耗尽**：父块查询走 MySQL 会迅速打满连接池 —— 这正是加 Redis 的原因；
3. **缓存击穿**：热点父块 TTL 到期瞬间大量回表 —— 加互斥锁或逻辑过期；
4. **写入放大**：批量入库时逐条 upsert —— 合并为批量接口（本项目一次 `upsert`）；
5. **向量库段膨胀**：频繁 `flush` / 小批量写入会产生大量小段 —— 关闭 flush 并用批量写入。

### Q31. 如果父块内容经常更新，架构要怎么改？

1. **缓存策略**：从「写入即覆盖」改为「写库后删除 + 延迟双删」，
   或引入消息队列异步失效；
2. **向量重建**：内容变更后 `content_hash` 变化 → 父块 id 变化 → 旧子块需删除
   （本项目 `force_reindex` 已实现「先删后建」）；
3. **版本化**：父块表增加 `version`/`valid_from`，检索时按版本过滤，支持回滚；
4. **增量重建**：用 binlog 订阅驱动重建，避免全量重灌。

### Q32. 多租户场景怎么隔离？

优先用 **Milvus 标量过滤**而不是建多个集合：给子块增加 `tenant_id` 字段，
检索时传 `expr='tenant_id == "t1"'`。优点是资源利用率高、运维简单；
缺点是过滤字段基数高时性能会下降，需要评估选择性。

本项目的 `ChildChunkStore.hybrid_search(expr=...)` 与
`AnnSearchRequest(expr=...)` 已预留该能力，只需在 schema 里加字段。

### Q33. 医疗、法律这类高准确性场景怎么降低幻觉？

1. **Prompt 层**：强制「仅依据给定片段」+ 提供「无法回答」的标准句式
   （本项目 Prompt 已含这两条）；
2. **检索层**：提高召回质量（混合检索 + Rerank）、低分父块过滤
   （`SCORE_RATIO_THRESHOLD`）；
3. **结构层**：父子分块本身就在减少「上下文残缺导致的臆测」；
4. **产品层**：强制输出引用 `[父文档ID: x]`，提供原文跳转，人工可核验；
5. **流程层**：高风险问题走人工复核，模型只做「草稿生成」。

### Q34. 这套架构的检索质量怎么评估？

三个层次：

- **检索层**：`Recall@k`（正确父块是否进入结果）、`MRR`（正确结果的排名）；
- **上下文层**：人工抽查送入模型的父块是否自洽完整（父子分块的核心指标）；
- **端到端层**：用标注问答对测答案准确率、引用正确率。

注意：**只盯向量相似度分数是不够的**，父子分块的最终目标是提升大模型回答质量，
而不是提升检索分数本身。

### Q35. 如何把 QPS 从 10 提到 100？

按性价比排序：

1. **缓存前置**：父块内容走 Redis（本项目已做），命中率做上去收益最大；
2. **`MGET` 批量化**：消除 N+1；
3. **并发化**：向量化、Milvus 检索、Redis 取父块可以部分并行；
4. **HNSW `ef` 下调**：牺牲少量召回换延迟（先用离线评估确认可接受）；
5. **LLM 流式输出**：感知延迟大幅下降（首 token 时间）；
6. **多实例 + 无状态服务**：向量库与缓存本身就是共享的，应用层可水平扩展；
7. **持久化连接**：向量库 gRPC channel、MySQL 连接池、Redis 连接池都要复用。

## 四、高频考点与深度追问（10 题）

### Q36.（高频）父子分块比固定分块到底提升在哪？请量化。

固定分块必须在「召回率」和「上下文完整度」之间二选一；父子分块同时满足。
本项目实测：父块 726~1314 字（保证上下文完整）、子块 235~257 字（保证检索聚焦），
粒度比约 4:1。而只按标题切时粒度比退化到 1.2:1，等于没有父子结构。

代价是：**存储放大**（同一内容存两份）、**写入变复杂**（三处一致性）、
**需要额外的去重步骤**（`parent_id` 聚合）。是否值得取决于文档长度与问答质量要求。

### Q37.（高频）如果检索不到答案，你会按什么顺序排查？

1. **数据是否入库**：`GET /api/v1/stats` 看父块数与子块数是否 > 0；
2. **向量维度是否匹配**：换过 Embedding 模型但没重建集合（必查项）；
3. **稀疏词表是否一致**：`data/index/vocab.json` 与入库时是否同一份
   （不一致 → 稀疏分支静默返回空）；
4. **单分支对比**：用 `POST /api/v1/compare` 看是稠密失效还是稀疏失效；
5. **分块是否合理**：`chunk_stats` 看块长是否异常（过短/过长）；
6. **低分过滤是否过狠**：`SCORE_RATIO_THRESHOLD` 是否把正确父块滤掉了；
7. **Prompt 是否误导**：模型答「无法回答」时，确认父块确实已送入（响应里有 `parents`）。

### Q38.（高频）为什么稀疏向量的下标映射这么重要？

因为 Milvus 只认整数下标，它不知道「安装」这个词。
如果入库与查询使用两份不同的词表（例如进程重启后词表丢失、重新按出现顺序编号），
同一个词在下标空间里对不上，**稀疏检索会静默返回空结果** —— 不抛异常、不报错，
表现为「稠密分支正常、稀疏分支永远没贡献」，极难排查。

所以工程上必须：词表落盘（`vocab.json`）、跨进程复用、变更时重建索引。

### Q39.（高频）`flush`、一致性级别、`row_count` 三者的关系？

- 写入后数据进入 WAL 与 memtable，**是否可见**由一致性级别决定；
- `flush` 把 memtable 落盘成 segment，**代价极高**，但会让 stats 立刻更新；
- `Bounded`（默认）下不 flush 时，`get_collection_stats().row_count` 长期为 0，
  但它**不代表数据没写入**；
- 正确组合：`consistency_level="Strong"`（读可见性）+ 不 flush（性能）+
  `query(count(*))`（准确统计）。

### Q40.（高频）你的父块打分公式为什么用乘法而不是加法？

见 Q18。核心是**尺度适配**：融合策略不同，分数尺度差一个数量级
（RRF `0.03` vs 稠密余弦 `0.5`）。固定加法偏置只能适配其中一种，
乘法是**尺度无关**的，两种情况都保持相同的相对影响。
这是「算法要对自己的输入分布有假设」的典型案例 —— 换融合策略时必须重新审视所有打分逻辑。

### Q41.（深度）如何避免超长块？

朴素的固定窗口切分遇到「整段没有句末标点」的文本（代码块、表格、清单、
压缩英文）会产出巨型块。本项目实测：一段 2900 字、仅用顿号分隔的文本，
最初产出了 **1 个 2900 字父块 + 1 个 2900 字子块**，父子分块完全失效。

修复方案是两级兜底：先按次级分隔符（顿号/逗号/分号/冒号）切；
若仍超过目标大小，再按字符窗口硬切。**必须有兜底分支**，
否则任何「意料之外的长文本」都会污染整个索引。

### Q42.（深度）多层缓存怎么设计？

推荐两级：**进程内 LRU（本地热父块）+ Redis（全量）**。

- 进程内缓存延迟 ~0.01ms，但多实例间不一致、容量受限于单机内存；
- Redis 延迟 ~0.3ms，多实例共享、容量可控。

策略：本地缓存设很短 TTL（秒级）或配合版本号失效；Redis 作为权威缓存。
风险是本地缓存导致**更新不一致窗口**，对父块这种「几乎不变」的数据可以接受，
对高频变更的数据应慎用。

### Q43.（深度）向量库里的 `content` 字段要不要存？

要存，但有取舍：存了子块原文，才能做结果展示、高亮、rerank 与调试；
代价是返回体积和内存占用变大。

更激进的做法是只存 `chunk_id` 与 `parent_id`，原文放 MySQL/Redis ——向量库回归
「纯索引」定位。缺点是每次结果展示都要回表，且 rerank 需要额外取文本。

本项目选择**存子块原文**（子块仅几百字符，成本可接受），换来调试便利与
`explain` 对比能力。这是一个典型的「按数据规模与排查需求做取舍」的决策。

### Q44.（深度）入库时如何保证不重复计算向量？

三层防护：

1. **父块层**：`(doc_id, content_hash)` 唯一索引，内容没变就复用原 `parent_id`，
   不重复插入；
2. **子块层**：`chunk_id = sha256(parent_index|index|content)`，内容没变主键就相同，
   `upsert` 覆盖而非新增；
3. **业务层**：`force_reindex` 只在明确需要时使用；增量入库走「内容变更检测」。

如果要进一步省算力，可以在 `_build_child_rows` 前先 `query` 已存在的 `chunk_id`，
跳过向量计算 —— 本项目为保持代码清晰未做该优化，这是可优化点。

### Q45.（深度）如果要从零重做这个项目，你会改变什么？

1. **向量模型优先**：先用真实 BGE-M3 定下维度与语义空间，再设计集合，
   避免「先跑通后迁移」导致的重建成本；
2. **分块先做评估集**：先准备 20~30 个标注问答对，再调 `parent_size/child_size`，
   而不是靠肉眼看块长；
3. **一致性用外置机制**：把「父块写入 + 缓存失效 + 向量重建」交给消息队列或
   binlog 订阅，而不是在应用层顺序执行；
4. **词表生命周期显式化**：词表版本号写进集合元数据，检索时校验版本，
   版本不一致直接报错，而不是静默返回空；
5. **一开始就拆分 `explain` 与生产路径**：`explain=true` 会额外跑两路检索，
   生产环境默认关闭，避免误用导致延迟翻倍。
