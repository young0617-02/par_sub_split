# 分步骤学习路径

> 目标：不只是「跑起来」，而是能**从零设计并解释**这套父子分块 RAG 架构。
> 每个阶段都有明确的验证方式，做完能自测是否真正掌握。

## 总览

| 阶段 | 主题 | 核心问题 | 建议耗时 | 产出 |
| --- | --- | --- | --- | --- |
| 1 | 环境与三存储认知 | 三个存储各自解决什么问题？ | 1~2 h | 能独立拉起环境并验证连通性 |
| 2 | 单存储基本操作 | 表怎么建、集合怎么建、缓存怎么读？ | 3~4 h | 能手工完成一次写入与读取 |
| 3 | 父子分块算法 | 为什么两级切分？边界怎么保证？ | 3~4 h | 能画出分块结构并解释参数 |
| 4 | 向量化与混合检索 | 稀疏和稠密各擅长什么？怎么融合？ | 4~6 h | 能看懂三路对比结果 |
| 5 | 三存储编排 | 一次写入如何在三处保持一致？ | 4~6 h | 能讲清入库/查询两条链路 |
| 6 | 服务化与优化 | 怎么发现瓶颈？怎么调参？ | 4~6 h | 能做性能对比与参数实验 |

## 阶段 1：环境与三存储认知（1~2 h）

**学什么**

- 三个存储的角色边界：MySQL = 事实来源，Redis = 加速缓存，Milvus = 向量索引；
- Docker 容器与宿主机端口映射（本项目 MySQL 宿主机端口是 **9999**，不是 3306）。

**动手**

```bash
docker compose ps                            # 确认 5 个服务都在运行（par_sub_* 容器）
docker compose up -d                         # 未启动时一键拉起全部依赖
docker exec par_sub_redis redis-cli ping      # 期望 PONG
docker exec par_sub_mysql mysqladmin -uroot -p123456 ping   # 期望 mysqld is alive
```

**理解要点**

| 问题 | 答案 |
| --- | --- |
| 为什么不用一个数据库搞定？ | 三者优化的目标不同：关系一致性、亚毫秒读、近似最近邻检索。混在一层会互相拖累 |
| 为什么 MySQL 端口是 9999？ | 宿主机 9999 → 容器 3306，避免与已有 MySQL 冲突。**这个映射关系是本项目最常见的配置错误来源** |
| Milvus 为什么连不上？ | 本机 Milvus 开启了鉴权（`COMMON_SECURITY_AUTHORIZATIONENABLED=true`），必须带 `MILVUS_TOKEN=root:123456` |

**验证**：`python scripts/init_db.py` 输出三个 `[OK]`。

## 阶段 2：单存储基本操作（3~4 h）

### 2.1 MySQL：表设计与幂等

**动手**

```bash
python -c "from app.clients.mysql import init_schema; print(init_schema())"
docker exec par_sub_mysql mysql -uroot -p123456 -e "USE par_sub_split; SHOW CREATE TABLE parent_document_t\G"
```

**要理解的设计点**

1. 为什么主键必须是**自增整数**（它要成为 Redis key 与 Milvus `parent_id`）；
2. 为什么唯一索引建在 `(doc_id, content_hash)` 而不是单独 `content_hash`；
3. 为什么用 `session.flush()` 而不是 `commit()`。

**自测**：同一篇文档连续入库两次，父块数量应该不变（`parent_ids` 完全相同）。

### 2.2 Redis：缓存与批量读取

**动手**

```bash
docker exec par_sub_redis redis-cli --scan --pattern "psd:parent:*"
docker exec par_sub_redis redis-cli GET psd:parent:1
docker exec par_sub_redis redis-cli MGET psd:parent:1 psd:parent:2 psd:parent:3
docker exec par_sub_redis redis-cli GET psd:cache:hits
# 若容器名不是 par_sub_redis（早期独立部署的机器），用 docker compose ps 确认真实名称
```

**要理解的设计点**

- `MGET` 与循环 `GET` 的往返次数差异（N 次 → 1 次）；
- 为什么统计计数写进 Redis 而不是进程内存；
- 为什么 `SCAN` 比 `KEYS` 安全。

### 2.3 Milvus：集合、索引、检索

**动手**

```bash
python -c "
from app.clients.milvus_client import get_chunk_store
import json
print(json.dumps(get_chunk_store().describe(), ensure_ascii=False, indent=2))
"
```

**要理解的设计点**

| 项 | 取值 | 原因 |
| --- | --- | --- |
| 稠密索引 | HNSW + COSINE | 向量已 L2 归一化；余弦不受模长影响 |
| 稀疏索引 | SPARSE_INVERTED_INDEX + **IP** | BM25 权重需要加权求和，不能余弦归一化 |
| 一致性 | **Strong** | 写入即可检索，避免用 `flush` 换可见性（差 140 倍） |
| 主键 | 内容 sha256 | 配合 `upsert` 实现幂等 |

## 阶段 3：父子分块算法（3~4 h）

**学什么**

- 「检索粒度」与「生成粒度」的矛盾是 RAG 的结构性难题；
- 父子分块 = 用子块检索 + 用父块生成；
- 子块**绝不跨越父块边界**是硬约束（`parent_id` 只能存一个值）。

**动手**

```bash
python -c "
from app.services.chunker import split_document, chunk_stats
text = open('data/samples/03-父子分块检索优化手册.md', encoding='utf-8').read()
parents = split_document(text)
print(chunk_stats(parents))
for p in parents:
    print(f'父块#{p.index} [{p.heading_path}] {p.char_count}字 -> {len(p.children)} 子块')
    for c in p.children: print('   子块', len(c.content), '字')
"
```

**关键实验**：改参数观察影响

```bash
python -c "
from app.services.chunker import split_document, chunk_stats
import itertools
text = open('data/samples/03-父子分块检索优化手册.md', encoding='utf-8').read()
for ps, cs in [(600,200),(1200,280),(2400,400)]:
    s = chunk_stats(split_document(text, parent_size=ps, child_size=cs))
    print(f'父{ps}/子{cs} -> 父块{s[\"parent_count\"]}个 均长{s[\"avg_parent_chars\"]} | 子块{s[\"child_count\"]}个 均长{s[\"avg_child_chars\"]}')
"
```

**自测**

1. 为什么切分顺序必须是「先父后子」而不是「先小子后合并」？
2. 如果只按 Markdown 标题切父块，会出现什么问题？（答案：父块退化成子块粒度，实测均长仅 206~266 字）
3. 重叠比例设 10% 和 50% 各有什么代价？

## 阶段 4：向量化与混合检索（4~6 h）

### 4.1 稀疏向量：BM25 与词表持久化

**动手**

```bash
python -c "
from app.services.sparse import get_sparse_encoder
enc = get_sparse_encoder()
print(enc.describe())
print('查询编码:', sorted(enc.encode('父子分块与稀疏向量').items(), key=lambda x:-x[1])[:5])
"
```

**必须理解的坑（面试高频）**

1. 词表**必须落盘**：下标不一致 → 稀疏检索**静默返回空**，不报错；
2. 必须先 `fit()` 再 `encode()`，否则新词被整批丢弃；
3. 空稀疏向量会被 Milvus 拒绝，需要占位下标 0；
4. IDF 依赖 `df / N / avgdl`，必须跨请求复用。

### 4.2 稠密向量：Provider 抽象

```python
EMBEDDING_PROVIDER=hash    # 离线跑通（默认）
EMBEDDING_PROVIDER=api     # OpenAI 兼容服务
EMBEDDING_PROVIDER=local   # sentence-transformers / BGE-M3
```

**要点**：`hash` 是**确定性特征哈希替身**，只保证链路跑通；生产必须换真实模型。
切换后**必须重建集合**，因为维度与语义空间都变了。

### 4.3 混合检索与融合

**动手（关键实验）**

```bash
python -c "
import json, urllib.request
req = urllib.request.Request('http://127.0.0.1:8000/api/v1/compare',
    data=json.dumps({'query':'SPARSE_FLOAT_VECTOR 的下标要注意什么？','top_k':10,'final_top_k':3}).encode(),
    headers={'Content-Type':'application/json'})
print(json.dumps(json.loads(urllib.request.urlopen(req).read()), ensure_ascii=False, indent=2)[:1500])
"
```

同一个 query 分别看 `dense_only` / `sparse_only` / `hybrid`，重点观察
`analysis.only_in_sparse` —— 那些就是**只有关键词分支能召回的父块**。

**自测**

1. RRF 的公式是什么？为什么 `k` 取 60？
2. 为什么加权融合比 RRF 更需要调参？
3. 为什么「多子块命中加成」必须用乘法？（RRF 分数 0.03 量级 vs 稠密 0.3 量级）

## 进阶方向

1. **Rerank 精排**：Milvus 召回 20 个子块后用 Cross-Encoder 精排到 5 个。
   注意：应作用于**子块**还是**父块**？各自的代价是什么？
2. **查询改写与多路召回**：HyDE、查询扩展、子问题拆解，提升稀疏分支的覆盖率。
3. **多级缓存**：进程内 LRU（热父块）+ Redis（全量）两级，进一步降延迟。
4. **增量更新与一致性**：订阅 MySQL binlog 驱动缓存失效与向量重建。
5. **效果评估体系**：构建标注问答对，度量召回率、上下文完整度、端到端准确率。
6. **多租户与权限过滤**：利用 Milvus 标量过滤（`expr`）做租户/部门隔离 ——
   本项目 `hybrid_search(expr=...)` 已预留该能力。
